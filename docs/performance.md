# 性能数据

所有数字都是实测值，测量环境如下。没有测过的项目会明确标注。

- 机器：AMD EPYC（4 逻辑核）、6 GB 内存、Windows 10 Pro x64（19045）
- 软件：Python 3.13.18、uv 0.13.6、Mihomo v1.19.33（Go 1.26.9 编译的验证适配器）
- 日期：2026-11-08
- 数据：v1 固定提交 `5bcb86f` 的 `my.wei` 及其引用的 210 个真实上游来源（当日内容），以及固定种子生成的合成数据

## 真实 profile

| 步骤 | 耗时 | 说明 |
| --- | ---: | --- |
| `fetch`（冷启动，无快照） | 29 s | 210 个来源全部下载并解析，0 失败；快照共 12 MB |
| `fetch`（已有快照，上游未变） | 6 s | 210 个来源全部返回 HTTP 304 |
| `build` | 18.5 s | 21 组规则，输出 59 个规则文件 |
| `verify --level semantic` | 28 s | 约 74 万个域名探测、14 万个地址探测，0 不一致 |
| `verify --level kernel` | 约 50 s | 5 万个请求在真实 Mihomo 上对照，0 不一致（含一次构建） |

下载层的 Happy Eyeballs 修复前，本机因 IPv6 不通，冷启动 `fetch` 需要 17 min 14 s。

### 优化效果

同一批合集成员，「未优化」指按合集原样合并后的成员（仍分为 domain/ipcidr/classical 三类），「优化后」是实际发布的产物：

| 指标 | 未优化 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 规则条目 | 638,383 | 200,911 | −68.5% |
| 文件体积 | 13.7 MB | 4.4 MB | −67.8% |
| classical 条目（逐条比对） | 476 | 356 | −25.2% |
| Mihomo 加载全部 provider | 8.3–8.8 s | 3.1–3.4 s | 约 −62% |
| 单次完整规则匹配（平均） | 6.5–6.9 µs | 6.4–7.2 µs | 无明显差异 |

加载与匹配耗时来自内核层验证（`verify --level kernel`）连续三次运行的范围。单次匹配是 5 万个请求走完整条规则表的平均值；由于 Windows 上单次计时粒度较粗，只统计整批总耗时再求平均。

**如何理解**：Mihomo 的 domain 与 ipcidr provider 在加载时会自行排序、去重并建成紧凑索引，单次查询成本与条目数基本无关，所以去重不会让单次匹配变快。去重减少的是加载耗时、内存与文件体积，对订阅刷新和移动设备更明显。真正影响匹配速度的是两件事：能进集合的条件都进集合；目标 IP 条件不触发 DNS（本 profile 中只有手写的 `GEOIP,CN` 会请求解析，这是有意为之）。
